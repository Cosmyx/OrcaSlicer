# 0133. Machine-read names use SLIC3R_APP_KEY

## Status

Accepted. Amended after integration build 44545583808: no row rewires the
AppImage desktop entry any more (decision 0132).

## Context

Renaming `SLIC3R_APP_NAME` would also change text that programs read: the
G-code header (`; generated by OrcaSlicer ...`), which OrcaSlicer, printers
and post-processing tools use to detect the producer and to load the config
back; the HTTP User-Agent; the generator of the G-code statistics JSON; and
the producer table of the G-code processor.

## Decision

- Patch rows rewire these five sites to `SLIC3R_APP_KEY` (still
  `OrcaSlicer`): `header_slic3r_generated()` in `utils.cpp`, the header
  check in `ConfigBase::load_from_gcode_file` (`Config.cpp`), the
  User-Agent in `Http.cpp`, the generator in `GCodeStatistics.cpp`, and the
  producer row in `GCodeProcessor.cpp`. Each was checked on DEV.
- Guard G8 keeps the app key safe: after apply, no line naming
  `SLIC3R_APP_KEY` may disappear from a patched file, except a line a patch
  row names the key in on purpose; the key's definition never changes. No
  committed row does so any more: the AppImage desktop entry `Name=` keeps
  the key, because appimagetool names the file after it (decision 0132). Lines
  that start naming the key (the sites above) are always fine.
- `tests/cosmyx/test_gcode_header_producer.cpp` checks, on the branded tree
  the CI builds, that the header starts with the app key, contains the
  literal the processor detects (`generated by OrcaSlicer`), and that G-code
  from this build and from OrcaSlicer both load.

## Consequences

- G-code from a CosmoSlice build is indistinguishable from OrcaSlicer's for
  every tool, and CosmoSlice loads OrcaSlicer G-code.
- Removing it: drop the five rows; the header then says CosmoSlice, and
  OrcaSlicer refuses to load the config of such files.
